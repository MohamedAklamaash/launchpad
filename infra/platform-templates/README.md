# Platform template bucket — hosted CloudFormation templates

**Platform-owned, like `infra/platform-dns/` and `infra/platform-builder/`.** Everything
under `deployment-services/infrastructure-service/infra/aws/` provisions the *customer's*
account; this provisions Launchpad's own, to host the two generated CloudFormation
templates (F8 ticket 1) that back the dashboard's "Launch stack" quick-create link. It is
the third platform-owned tree in the repo — see root `CLAUDE.md`'s "Two trees are the
exception" section, which this ticket renames to "three" — and follows the separation
rule `platform-dns` set: this is not reachable by the infrastructure-service provisioning
worker's credentials, and it provisions nothing in a customer account.

See `plan/F8-cloudformation-onboarding.md`, Decision §3 ("Hosting"), for the full design.

## Why this exists

`cloudformation:CreateStack`'s `TemplateURL` parameter — the one the console's
quick-create link uses — only resolves against an S3 object location; it is not a general
HTTPS fetch. That's an AWS API constraint, not a choice this design made (see the plan's
Non-goals). The two templates generated by
`deployment-services/infrastructure-service/api/cloud_providers/aws/iam_policy/generate.py`
(`cloudformation/launchpad-deployment-role.{ecs-fargate,eks}.template.json`) therefore need
a home in S3, pinned per git ref so a customer's quick-create link never points at a moving
target.

**The backend itself does not read from this bucket.** `cfn_onboarding.py`'s
`CreateChangeSet` call (the refresh flow, plan §5) passes `TemplateBody` from the
committed file on disk directly — `TemplateURL`'s S3-only constraint is specific to
`CreateStack`'s browser-driven quick-create link, not to that boto3 call. This bucket
exists purely to serve the frontend's quick-create link and the manual "Specify template"
console flow for customers who can't use a quick-create link (plan §3's URL-length/
`ExternalIds`-count degrade cases).

## What's here

| File | Contents |
|---|---|
| `versions.tf` / `providers.tf` | Provider pin, default tags, `aws_caller_identity`/`aws_region` data sources. No backend block — left to the operator, same as `platform-dns`/`platform-builder`. |
| `variables.tf` | `aws_region` (default `us-east-1`; has no bearing on the IAM resources the templates themselves create — IAM is global — only on where this bucket's own object metadata is filed) and `templates_prefix` (default `templates`). |
| `s3.tf` | One S3 bucket: `BucketOwnerEnforced` ownership controls, versioning on, SSE-S3 (AES256 + bucket key), Block Public Access with ACLs blocked/ignored but the *policy* flags left open so a scoped bucket policy can grant public `s3:GetObject`, and that bucket policy itself — public read of `s3:GetObject` only, only under `templates_prefix`, no `s3:GetObjectVersion`, no `s3:ListBucket` anywhere — plus the same deny-insecure-transport statement `platform-builder`'s sources bucket uses. |
| `outputs.tf` | `bucket_name`, `bucket_arn`, `templates_prefix`, and `template_base_url` — the exact value to hand the frontend's `NEXT_PUBLIC_LAUNCHPAD_CFN_TEMPLATE_BASE_URL`. |
| `publish.sh` | The release-action script: conditional-PUT publish of both generated templates, keyed by a resolved git commit SHA. |

## Apply it in a dedicated AWS account

Not a customer account, and ideally not the same account that holds
`LAUNCHPAD_PLATFORM_PRINCIPAL_ARN`'s trust-policy principal, for the same blast-radius
reasoning `platform-builder`'s README gives. This bucket is deliberately public-readable
under its prefix, so the account it lives in must not have **account-level** S3 Block
Public Access forced on — that setting silently overrides every bucket-level setting below
it, and would make `aws_s3_bucket_public_access_block.templates`'s `block_public_policy =
false` / `restrict_public_buckets = false` ineffective.

```bash
cd infra/platform-templates
terraform init
terraform apply
```

No backend configuration is defined — add one (S3 + DynamoDB lock, or your platform's
convention) before a second person needs to apply this.

The AWS console will show this bucket's access as "Public" (for the prefix) — that is
expected, not a misconfiguration to fix.

## Create the publisher principal — out of band

Same reasoning `platform-dns` gives for its DNS-writer access key and `platform-builder`
gives for its build-launcher principal: a long-lived secret has no business sitting in
Terraform state.

Write access to this bucket is a trust-boundary credential, not an incidental one — a
template is what grants `LaunchpadDeploymentRole` its trust policy and permissions, so a
tampered template could repoint the trust principal at an attacker-controlled account or
widen the policy undetected. Create a dedicated IAM user or role out of band, grant it
**only**:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::<bucket_name output>/<templates_prefix output>/*"
    }
  ]
}
```

No `s3:DeleteObject`, no `s3:PutBucketPolicy`, no broader `s3:*`. Combined with versioning
and the conditional-PUT publish step below, this principal can neither overwrite nor
silently remove a ref that's already live — the write itself fails closed.

## Publish a ref — the standing release action

Run after `generate.py --write` (or any commit where the committed templates are already
current) and after the templates are merged to the ref you intend to publish:

```bash
BUCKET=$(terraform -chdir=infra/platform-templates output -raw bucket_name)
infra/platform-templates/publish.sh "$BUCKET" <git-ref>
```

`<git-ref>` can be a tag, branch, or short SHA — `publish.sh` resolves it to a full commit
SHA with `git rev-parse --verify "<ref>^{commit}"` before using it as the S3 key segment,
so the published key is never a moving branch name. It runs `generate.py --check` first
(refuses to publish drifted templates) and uploads both files to
`s3://$BUCKET/<templates_prefix>/<resolved-sha>/<template-file>` with
`aws s3api put-object --if-none-match '*'` — the AWS CLI's documented conditional-PUT
flag (confirmed supported in `aws-cli/2.35.15`; if your CLI predates this flag, upgrade
rather than drop the condition, since dropping it reintroduces exactly the silent-overwrite
risk this step exists to close). A re-run against an already-published ref exits
successfully without writing (reported as "already published", not an error) — the CLI
surfaces this as an `AtLeastOnePreconditionFailed`/`PreconditionFailed` response from the
conditional PUT, not a local check, so the no-overwrite guarantee holds even against a
concurrent publisher.

Bucket versioning stays on as defense-in-depth against an accidental delete of an already
published key — the conditional PUT is what actually prevents the overwrite in the first
place.

**This script never runs `terraform apply`/`plan` and uploads nothing on its own** unless
you invoke it; it is not wired into CI. CI only runs `terraform fmt -check` and an offline
`init -backend=false && validate` against this directory (see `.github/workflows/ci.yml`'s
`check-terraform` job) — no AWS credentials, no state, same posture as `platform-dns`/
`platform-builder`.

## Wiring the published ref into the frontend

```
NEXT_PUBLIC_LAUNCHPAD_CFN_TEMPLATE_BASE_URL=<template_base_url output>
NEXT_PUBLIC_LAUNCHPAD_CFN_TEMPLATE_REF=<resolved-sha publish.sh printed>
```

See `launchpad-frontend/lib/onboarding-cloudformation.ts` and `env.example` — the
frontend builds the final template URL as `${BASE_URL}/${REF}/${template-filename}`,
which is exactly `s3://<bucket>/<templates_prefix>/<ref>/<template-file>` rendered as an
HTTPS virtual-hosted-style URL. Both env vars are mandatory once CFN onboarding is
enabled; there is deliberately no hardcoded bucket name anywhere in the frontend to fall
back to.

## What's intentionally not here

- **Any backend wiring.** `api/services/cfn_onboarding.py` reads the generated templates
  straight off disk (`TemplateBody`), not from this bucket — see "Why this exists" above.
  Nothing in `deployment-services/` needs this bucket's name or URL.
- **A backend block.** Left to the operator, matching `platform-dns`/`platform-builder`.
- **The publisher IAM principal.** Created out of band, above — same pattern as
  `platform-dns`'s DNS-writer access key and `platform-builder`'s build-launcher
  principal.
- **CloudFront or any non-S3 fronting.** Foreclosed by `TemplateURL`'s own API contract,
  not a deferred optimization — see plan §3's Non-goals.
- **Any apply/upload performed by this change itself.** This PR adds the Terraform and
  the publish script only; nothing in it has been applied against real AWS, and no
  object has been uploaded. `terraform fmt -check` and an offline `validate` are the only
  checks run.
