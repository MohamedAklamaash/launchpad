# Launchpad IAM Policies

## Overview

This document defines the IAM policies required for Launchpad to operate in your AWS account.

---

## Automated Setup (Recommended)

**You do not run these scripts by hand from this doc.** The Launchpad dashboard generates
the exact command — with your infrastructure's IDs, callback URL, and one-time onboarding
token pre-filled — when you create an infrastructure. Copy it from there and run it in a
shell with access to your AWS account. See the
[User Onboarding Guide](./USER_ONBOARDING_GUIDE.md#step-3--run-the-aws-setup-command).

The generated bootstrap command looks like:

```bash
export LAUNCHPAD_INFRA_ID=<your-infra-uuid>
export LAUNCHPAD_EXTERNAL_ID=<your-infra-uuid>
export LAUNCHPAD_CALLBACK_URL=https://<gateway>/api/infrastructures/onboarding/callback
export LAUNCHPAD_ONBOARDING_TOKEN=<one-time-token>
export LAUNCHPAD_PLATFORM_ACCOUNT_ID=<launchpad-platform-account-id>
export LAUNCHPAD_PLATFORM_USER=<launchpad-platform-iam-user>
curl -sSL https://raw.githubusercontent.com/MohamedAklamaash/launchpad/<pinned-ref>/app_scripts/create_aws_role.sh | bash
```

The script creates:
- IAM role: `LaunchpadDeploymentRole`
- IAM policy: `LaunchpadDeploymentPolicy`
- A trust relationship scoped to the Launchpad platform principal **and** your
  infrastructure's `ExternalId`
- A callback to Launchpad that verifies the token and starts provisioning

It is idempotent: re-running refreshes the policy **and** trust policy in place. Re-running
it with a script API key is also the refresh path for when Launchpad's required permissions
widen — see [Keeping the policy current](#keeping-the-policy-current).

---

## Automated Setup — CloudFormation

If you prefer a GUI over a shell command, create your infrastructure in the dashboard and
use the **Launch stack** quick-create link on the CloudFormation tab instead of running
`create_aws_role.sh`. This provisions the exact same `LaunchpadDeploymentRole` +
`LaunchpadDeploymentPolicy` as the script, generated from the same `policy.json` source of
truth and checked for drift by the same CI gate — the two onboarding paths can never grant
different permissions.

The link opens the AWS console pre-filled with:
- the CloudFormation template, hosted at a pinned, versioned URL shaped like
  `<platform-template-bucket>/<published-ref>/launchpad-deployment-role.<ecs-fargate|eks>.template.json`
  (one template per compute type — see [Template generation](../plan/F8-cloudformation-onboarding.md)
  for why there are two rather than one parameterized template)
- the stack's region, fixed to `us-east-1` — the role and policy this template creates are
  global IAM resources, so this has no bearing on where your applications actually run
- `ExternalIds`, `LaunchpadPlatformAccountId`, and `LaunchpadPlatformUser`, the same values
  the script's bootstrap command already exports

The console will prompt you to acknowledge **"I acknowledge that AWS CloudFormation might
create IAM resources with custom names"** (`CAPABILITY_NAMED_IAM`) — expected, since the
role and policy names are fixed (`LaunchpadDeploymentRole` / `LaunchpadDeploymentPolicy`),
not generated by CloudFormation.

Unlike the script, there's no shell posting a callback once the stack finishes. After the
stack reaches `CREATE_COMPLETE`, go back to the infrastructure's detail page in the
dashboard and click **Verify connection** — Launchpad assumes the newly created role itself
(the same `AssumeRole` path every other customer-account action already uses) and burns
your one-time onboarding token server-side. There is nothing to run locally and no token
ever appears in a CloudFormation parameter or the console's Parameters tab.

### Exclusivity: an account picks one method and keeps it

An AWS account onboards with **either** `create_aws_role.sh` **or** the CloudFormation
stack, never both at once, and there is no migration path between them in this release. The
CloudFormation-created role carries a `launchpad:managed-by=cloudformation` tag that
`create_aws_role.sh` checks for and refuses to touch (prints an error and exits rather than
silently rewriting the trust policy out from under the stack). The reverse holds too: a
script-created role has no such tag, so the dashboard won't offer you a quick-create link
once an authenticated script-onboarded infra already exists in that account.

If a second infrastructure onboards into an AWS account that already has a CloudFormation-
managed role, the dashboard does not offer another quick-create link (creating a second
stack would conflict with the first). Instead it shows you the merged `ExternalIds`
parameter value to paste into the existing stack's **Update** flow in the console — you
review and apply it yourself, the same "you drive every widening change" posture the script
already has.

Policy refreshes work the same way: the dashboard's CloudFormation refresh action opens a
change set against your existing stack rather than applying anything automatically — you
review the diff and execute it in the console, exactly like a stack update you'd make for
any other reason.

**Known limit**: if several Launchpad users share one AWS account with a mix of compute
types, the template the dashboard recommends at *create* time is based only on
infrastructures the person creating it can see — it cannot look at every infrastructure in
that AWS account without letting a user probe which compute types other tenants run. If
that under-recommends (for example, the account already has an EKS infra, and a new
ecs_fargate-only user's wizard doesn't know that), the next **refresh** performed by the
EKS infra's own owner re-proposes the wider template and corrects it. This is a narrow,
transient gap, not a permissions hole.

## Manual Setup

If you prefer to configure the role by hand instead of running the script, follow these
instructions. **You must include the `ExternalId` condition** — the backend always
presents it on AssumeRole, so a trust policy without it will fail with `AccessDenied`.

### Trust Policy for Cross-Account Role

Create role `LaunchpadDeploymentRole` with this trust policy. Replace
`<YOUR_INFRA_ID>` with the infrastructure UUID shown in the dashboard (this is the
`ExternalId`), and `<PLATFORM_ACCOUNT_ID>` / `<PLATFORM_USER>` with the values shown
on your infrastructure's detail page (also the `LAUNCHPAD_PLATFORM_ACCOUNT_ID` /
`LAUNCHPAD_PLATFORM_USER` the dashboard's generated script exports). These are not
fixed and must not be hardcoded, since they can be rotated on the platform side:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::<PLATFORM_ACCOUNT_ID>:user/<PLATFORM_USER>"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": { "sts:ExternalId": "<YOUR_INFRA_ID>" }
      }
    }
  ]
}
```

**Important**: 
- Platform Account ID / User: shown on your infrastructure's detail page in the
  dashboard. Ask your Launchpad admin if you're setting this up without dashboard
  access
- Role Name: `LaunchpadDeploymentRole` (exact name required)
- `sts:ExternalId`: your infrastructure UUID (required — prevents confused-deputy abuse)

## Setup Instructions

### Using the dashboard-generated script (Recommended)

Create the infrastructure in the dashboard and run the command it generates (it carries
your IDs + one-time token). See the
[User Onboarding Guide](./USER_ONBOARDING_GUIDE.md#step-3--run-the-aws-setup-command).
The script source lives at
[`app_scripts/create_aws_role.sh`](https://github.com/MohamedAklamaash/launchpad/blob/main/app_scripts/create_aws_role.sh);
the dashboard pins it to a specific commit and injects the env vars.

### Using AWS Console

1. **Create the policy**: IAM → Policies → Create policy → paste the deployment policy
   JSON above → name it `LaunchpadDeploymentPolicy`.
2. **Create the role**: IAM → Roles → Create role → "AWS account" → "Another AWS account"
   → Account ID `<PLATFORM_ACCOUNT_ID>` (shown on your infrastructure's detail page).
   **Check "Require external ID"** and enter your infrastructure UUID. Attach
   `LaunchpadDeploymentPolicy`. Name the role `LaunchpadDeploymentRole`.
3. **Verify the trust policy** matches the JSON above (principal scoped to
   `<PLATFORM_USER>` and the `sts:ExternalId` condition present).

## Keeping the policy current

The policy carries a **version number**. `create_aws_role.sh` reports the version it
applied on both its callbacks, so the dashboard knows exactly which policy your account
holds and flags the infrastructure when Launchpad ships a newer one — you no longer have
to wait for an `AccessDenied` to find out. The infrastructure detail page shows the
applied version alongside the current one.

When Launchpad adds capabilities, `LaunchpadDeploymentPolicy` gains actions and the
version is bumped. To pick up the new grants, re-run `create_aws_role.sh` — surfaced in
the dashboard as the *Refresh policy script*. The same idempotent script re-applies the
latest policy **and** trust policy in place; you don't recreate the role.

Accounts onboarded before versioning existed report no version and are shown as needing a
refresh — running it once records the current version and clears the flag.

Because one script owns the action list, the bootstrap and refresh paths can never drift
apart, so a refresh never narrows your permissions by accident.

A released version's permissions are frozen: widening the policy always produces a new
version rather than silently redefining one your account already applied.

The refresh snippet also carries a **per-user API key** (`LAUNCHPAD_API_KEY`) and posts to
a policy-refresh callback so Launchpad records who ran the refresh, against which account,
and when. The key is issued from the dashboard ("Generate API key"), shown once, stored
only as a hash, and rotated on re-issue. This attribution callback is best-effort — if it
can't reach Launchpad, the IAM update still succeeds.

## Permission Breakdown

### Why Each Permission is Needed

**EC2 (VPC Management)**:
- Create isolated network for your applications
- Public/private subnets for security
- NAT Gateway for outbound internet access
- Security groups for network isolation

**ECS Management**:
- Create cluster to run containers
- Register task definitions (container specs)
- Create services (long-running containers)
- Run and manage tasks

**ECR Management**:
- Store Docker images
- Pull images for deployment
- Manage image lifecycle

**ALB Management**:
- Expose applications to internet
- Route traffic to containers
- Health checks
- SSL/TLS termination (future)

**IAM Management**:
- Create service roles for ECS tasks
- PassRole to allow services to assume roles
- Manage permissions for created resources

**CodeBuild Management** (legacy cleanup only):
- Launchpad builds every image on its own infrastructure, not inside your account —
  nothing here starts or runs a build in your account
- `BatchGetProjects`/`DeleteProject` only, so Nuke can find and remove a per-infra
  CodeBuild project from before this change, if your account onboarded prior to it

**CloudWatch Logs**:
- Store application logs
- Debug issues
- Monitor application health

**RDS / ElastiCache / Secrets Manager**:
- Create and manage managed PostgreSQL, MySQL, Redis, and DocumentDB instances you
  provision from the dashboard, all inside your existing private subnets
- Store and retrieve the connection credentials Launchpad injects into your app
  containers — the plaintext credential never transits Launchpad's own systems

**S3**:
- Store Terraform state
- Version control infrastructure changes
- Backup and recovery

**DynamoDB**:
- Lock Terraform state during operations
- Prevent concurrent modifications
- Ensure consistency

**KMS**:
- Encrypt Terraform state
- Encrypt sensitive data
- Key management for resources

## Security Considerations

### Principle of Least Privilege

The policy grants broad permissions within specific services. This is necessary because:
- Infrastructure requirements vary per application
- Terraform needs flexibility to create resources
- Dynamic resource creation (IAM roles)

### Trust Policy Security

The trust policy is restricted to:
- **Specific Account**: the Launchpad platform account (shown on your infrastructure's
  detail page as `platform_account_id`)
- **Specific User**: the Launchpad platform IAM user (`platform_user`; not account root)
- **Specific ExternalId**: your infrastructure UUID — the backend must present this exact
  value on AssumeRole, which blocks confused-deputy abuse even if someone learns your
  account ID and role name
- **AssumeRole Only**: No direct access to resources

This is far more secure than trusting the entire account root.

### Recommendations

1. **Enable CloudTrail**: Monitor all API calls made by Launchpad
2. **Set Up Alerts**: CloudWatch alarms for unusual activity
3. **Regular Audits**: Review IAM policies and CloudTrail logs quarterly
4. **Resource Tagging**: All resources tagged with `ManagedBy: Launchpad`
5. **Cost Alerts**: Set up AWS Budgets to monitor spending

## Troubleshooting

### Permission Denied Errors

If you see permission errors:

1. **Check Role Name**: Must be exactly `LaunchpadDeploymentRole`
2. **Check Trust Policy**: Launchpad account ID must be correct **and** the
   `sts:ExternalId` condition must equal your infrastructure UUID. A missing or wrong
   ExternalId is the most common cause of `AccessDenied` right after onboarding —
   re-run the bootstrap/refresh script to fix the trust policy in place.
3. **Check Policy Attachment**: Policy must be attached to role
4. **Check Region**: Some services are region-specific
5. **Permissions widened?**: Re-run `create_aws_role.sh` (the dashboard's *Refresh policy*
   snippet) to pick up newly required actions.

### Testing Permissions

Test if role is configured correctly:

```bash
# Assume the role (the --external-id must match your infrastructure UUID,
# exactly as the backend sends it)
aws sts assume-role \
  --role-arn arn:aws:iam::<YOUR_ACCOUNT_ID>:role/LaunchpadDeploymentRole \
  --role-session-name test-session \
  --external-id <YOUR_INFRA_ID>

# Use temporary credentials to test
export AWS_ACCESS_KEY_ID=<from above>
export AWS_SECRET_ACCESS_KEY=<from above>
export AWS_SESSION_TOKEN=<from above>

# Test VPC creation
aws ec2 describe-vpcs
```

## Revoking Access

To revoke Launchpad's access:

1. **Delete Role**:
   ```bash
   aws iam delete-role --role-name LaunchpadDeploymentRole
   ```

2. **Delete Policy**:
   ```bash
   aws iam delete-policy --policy-arn arn:aws:iam::<YOUR_ACCOUNT_ID>:policy/LaunchpadDeploymentPolicy
   ```

WARNING: This will prevent Launchpad from managing your infrastructure. Clean up resources first.

**If your account was onboarded via CloudFormation** (check the infrastructure's detail
page in the dashboard, or look for the `launchpad:managed-by=cloudformation` tag on
`LaunchpadDeploymentRole`), deleting the role directly as above leaves the CloudFormation
stack behind in a drifted state — it still believes it owns a role and policy that no
longer exist, and a future update against it will fail. Delete the stack instead, and let
CloudFormation delete the role and policy as part of that:

```bash
aws cloudformation delete-stack --stack-name <your-stack-name> --region us-east-1
```

The stack name is shown on the infrastructure's detail page; it is not guaranteed to be
`LaunchpadDeploymentRole` — the quick-create link lets you rename it before creating the
stack. If Launchpad is still actively using the role when you delete the last
infrastructure in that account, it will tell you a stack delete is the one remaining
manual step rather than attempting it on your behalf — see the destroy-completion
notification for the exact console link.
